### 认证服务 `app/auth/`

- [ ] **03 · 认证时先验签再取身份**（黄金 Bug）
  - 现象：修改 JWT 中的 `user_id` 即可让仅调用 DecodeToken 的入口识别为另一用户；刷新服务也只解码身份。
  - 潜在的解决方案：将验签、有效期及声明校验封装为一个返回可信用户 ID 的方法；DecodeToken 和 RefreshToken 都调用它，不再直接读取未验证的 JWT payload。
  - 验收：无签名、过期、畸形 token 均拒绝；刷新不得基于未验证身份签发。
  - 定位：`app/auth/biz/service/decode_token.go`、`app/auth/biz/service/refresh_token.go`。

- [ ] **04 · 统一 token 撤销和会话策略**（黄金 Bug）
  - 现象：登出操作没有使正确的 Redis 密钥过期；新登录覆盖旧密钥，旧会话可能随之失效（多端登录是否需要保留待确认）。
  - 潜在的解决方案：先按产品规则决定单会话还是多会话；统一签发、验证、撤销使用的 Redis key，若支持多端则按 `jti` 保存会话并仅撤销目标 token。
  - 验收：登出后 token 确实失效；先确认是否支持多端登录，再设计密钥/会话存储及过期策略。**多端部分待确认。**
  - 定位：`app/auth/biz/service/deliver_token_by_rpc.go`、`app/user/biz/service/logout.go`。

### 用户服务 `app/user/`

- [ ] **05 · 禁止禁用账户登录**（白银 Bug）
  - 现象：账户被标记为禁用后，只要邮箱和密码正确，登录逻辑仍可能签发 token。
  - 潜在的解决方案：密码验证后、签发 token 前检查用户状态；若要求立即踢出已登录的禁用用户，验签时也要检查状态或会话版本。
  - 验收：禁用账户不能获得 token，补充状态测试。
  - 定位：`app/user/biz/service/login.go`。

- [ ] **06 · 请求处理过程不使用 Fatal**（白银 Bug）
  - 现象：登录认证 RPC 或用户更新验签失败时调用 `klog.Fatal`，可能使整个用户服务退出。
  - 潜在的解决方案：将业务处理中的 `klog.Fatal` 改为普通错误日志和明确的错误返回；仅在进程启动阶段无法恢复时选择退出。
  - 验收：RPC/认证错误返回给请求方，而不是使服务退出。
  - 定位：`app/user/biz/service/update_user.go`、`app/user/biz/service/login.go`。

- [ ] **07 · 核对用户注册模型与建表定义**（白银 Bug）

  - 潜在的解决方案：先确认实际迁移，再统一用户模型的 GORM 列映射与建表字段；注册时按约束提供用户名、手机号等必填值，配合迁移与集成测试。
  - 验收：对照实际迁移修正必填字段及列名，验证注册链路。**依赖真实库结构。**
  - 定位：`app/user/biz/service/register.go`、`docs/database/base.sql`。

- [ ] **08 · 注册返回真实用户 ID**（青铜 Bug）
  - 现象：不论新用户实际 ID 是多少，注册成功响应都返回 `UserId: 1`。
  - 潜在的解决方案：保留传给 `CreateUser` 的模型指针，成功插入后从其自增 ID 构造响应，而不是返回常量。
  - 验收：响应包含数据库创建后的用户 ID。
  - 定位：`app/user/biz/service/register.go`。

- [ ] **09 · 修复地址更新写回旧值**（白银 Bug）
  - 现象：用户提交新地址后，更新逻辑从数据库取出旧地址再写回，请求值未生效。
  - 潜在的解决方案：根据用户的地址关联，在地址表中写入请求的新地址；无地址时按业务规则创建记录，必要时将地址与用户更新放在同一事务。
  - 验收：使用新地址及正确的地址数据模型，不回写旧地址。
  - 定位：`app/user/biz/service/update_user.go`。

- [ ] **10 · 密码哈希失败立即返回**（白银 Bug）
  - 现象：密码哈希失败时错误被后续查询覆盖，可能将空哈希写入并报告更新成功。
  - 潜在的解决方案：将密码哈希单独赋值并立即检查返回错误；只有哈希成功才加入更新字段，避免后续查询覆盖该错误。
  - 验收：不能把哈希错误覆盖为后续查询结果；失败时数据库不变。
  - 定位：`app/user/biz/service/update_user.go`。

- [ ] **19 · 统一库存并发写入路径**（钻石 Bug）
  - 现象：在服务正常连接同一库存表的前提下，并发请求均可能通过先查库存的检查；商品编辑也可能把已扣库存覆盖回旧值。
  - 潜在的解决方案：用 `UPDATE ... SET stock=stock-? WHERE id=? AND stock>=?` 原子扣减并检查影响行数；商品资料修改与库存调整分离，库存调整走专用接口。
  - 验收：原子条件扣减并检查影响行数；商品编辑不能以旧库存覆盖并发扣减。**跨库存/商品模块。**

- [ ] **20 · 建立幂等的库存预留状态机**（钻石 Bug）
  - 现象：重复恢复可多次加库存；预留部分失败可能留下 Redis 标记；标记过期却不会恢复已扣的数据库库存，结算补偿失败还可能遗留不一致状态。
  - 潜在的解决方案：建立以 `(order_id, product_id)` 唯一标识的预留记录；在事务中扣库存并改变预留状态，恢复只允许 `reserved → released` 一次，过期用可靠任务及重试处理。
  - 验收：持久化管理预留、恢复、支付确认、过期与补偿；恢复幂等，多商品失败可回滚，超时可处理。**与结算服务协同。**
  - 定位：`app/stock/biz/service/reserve_item.go`、`app/stock/biz/service/recover_item.go`、`app/checkout/biz/service/checkout.go`。

- [ ] **21 · 明确预留数量语义**（白银 Bug）

  - 验收：以订单逐项数量为准；定义或移除请求级 `quantity`，覆盖多商品数量不一致测试。

  - 潜在的解决方案：以实际迁移为准确定唯一商品库存表；库存和商品服务统一表名、连接配置及模型映射，避免用两份互不一致的库存数据。

### 支付服务 `app/payment/`

- [ ] **34 · 正确处理 MQ 生产者初始化失败**（白银 Bug）
  - 现象：MQ 连接或资源声明失败后初始化错误被忽略，后续发送支付消息可能因生产者不可用而失败或 panic。
  - 潜在的解决方案：移除包级隐式建连，把生产者初始化放在启动阶段并逐层返回错误；只有 MQ 资源声明成功才启动 RPC 服务。
  - 验收：构造、交换机/队列声明失败时阻止服务就绪，不忽略错误。
  - 定位：`app/payment/biz/dal/rabbitmq/cardPayment.go`、`app/payment/biz/dal/rabbitmq/paymentProducer.go`。

- [ ] **35 · 统一支付结果的消息协议和路由**（黄金 Bug）
  - 现象：一端发送 `success`，另一端读取 `state`；即使消息送达也可能被判支付失败，部分环境路由键与绑定键还不匹配。
  - 潜在的解决方案：定义共享的支付结果事件结构，统一成功字段；分清请求/结果队列及路由键，按实际声明的绑定关系逐环境验证投递。
  - 验收：统一 `success/state`，对照各环境队列绑定做收发集成测试。**投递现状待验证，涉及结算服务。**
  - 定位：`app/payment/biz/dal/rabbitmq/`、`app/checkout/biz/dal/RabbitMQ/`、`app/checkout/conf/test/conf.yaml`。

- [ ] **36 · 确认支付消息实际送达**（黄金 Bug）
  - 现象：消息未匹配任何队列或未可靠投递时，发布调用仍可能返回成功，订单后续没有支付结果。
  - 潜在的解决方案：开启 publisher confirm，针对未路由消息设置 mandatory 并处理 Return；需要跨库原子性时使用 outbox/重试，避免只凭 Publish 无错误判定送达。
  - 验收：使用路由/发布确认或等效可靠投递方案；未送达不能报告成功。**涉及结算服务生产者。**

- [ ] **37 · 正确处理支付 HTTP 回调失败**（白银 Bug）

  - 潜在的解决方案：读取 HTTP 状态码，2xx 才视为成功；按业务约定区分重试与拒绝，向消息消费者返回可处理的错误。
  - 验收：检查非 2xx 状态并返回错误，避免失败请求被 ACK。
  - 定位：`app/payment/biz/dal/rabbitmq/PaymentHandler.go`、`app/payment/biz/dal/rabbitmq/consumer.go`。
